# PBN0027

*'X' is a non-nullable collection, but nothing assigns it when protobuf-net constructs the
instance; it is null whenever the payload does not carry it, and an empty collection is normally
not written at all.*

protobuf has no way to say "present, but empty": an empty collection is simply **not written**. So
on the receiving end the member is never touched, and keeps whatever construction left there. If
that is `null`, a sender holding `[]` leaves the receiver holding `null`.

Nothing warns about this. The member is declared non-nullable, so the compiler is satisfied that
reading it is safe, and the `NullReferenceException` turns up later, somewhere far from the contract,
and only for the messages that happened to have no elements. It is also where protobuf parts
company with JSON, which writes `[]` and so gets the collection back — a DTO that has always worked
with `System.Text.Json` can start failing the day it is sent over protobuf.

## Without `SkipConstructor`

protobuf-net creates the instance with its **parameterless constructor**, so the collection is safe
if an initializer or that constructor assigns it. It is not safe when nothing does — including the
usual ways of silencing the compiler's own CS8618 warning, which assign nothing at all:

``` csharp
#nullable enable
[ProtoContract]
public class Order
{
    [ProtoMember(1)] public List<OrderLine> Lines { get; set; } = null!;   // reported
    [ProtoMember(2)] public required List<string> Tags { get; set; }        // reported
    [ProtoMember(3)] public List<int> Codes { get; set; } = new();          // fine
}
```

An assignment in a constructor *with parameters* does not count either, since that is not the one
protobuf-net calls.

## With `SkipConstructor`

`[ProtoContract(SkipConstructor = true)]` creates the instance without running **any** constructor,
so every field starts out `null` — and that includes initializers, which the C# compiler places
inside the constructor. Here even `= new()` does not help:

``` csharp
#nullable enable
[ProtoContract(SkipConstructor = true)]
public class Order
{
    // the initializer never runs on deserialize: an order with no lines comes back with null here
    [ProtoMember(1)] public List<OrderLine> Lines { get; set; } = new();
}
```

It is sharper still when the member is not part of the contract at all. Nothing ever writes it, so
it is `null` after **every** deserialize:

``` csharp
#nullable enable
[ProtoContract(SkipConstructor = true)]
public record TestRecord(string[] Array); // no [ProtoMember]: Array is always null
```

## Fixes

Declare the member nullable. The value really can be null, and saying so makes the compiler ask
every reader to deal with it:

``` csharp
[ProtoMember(1)] public List<OrderLine>? Lines { get; set; }
```

Without `SkipConstructor`, initialize it — `= new()`, or assign it in the parameterless constructor.

With or without it, you can restore it in a deserialization callback, which protobuf-net runs on the
new instance. Any of `[ProtoBeforeDeserialization]`, `[ProtoAfterDeserialization]`,
`[OnDeserializing]` and `[OnDeserialized]` satisfies this warning, provided it assigns the member:

``` csharp
[ProtoContract(SkipConstructor = true)]
public class Order
{
    [ProtoMember(1)] public List<OrderLine> Lines { get; set; } = new();

    [ProtoAfterDeserialization]
    private void OnDeserialized() => Lines ??= new();
}
```

Or drop `SkipConstructor`, if nothing forces it. It is usually there because the type has no
parameterless constructor.

## What is not reported

- **Nullable members** (`List<T>?`), and members in code without nullable reference types enabled —
  those have promised nothing.
- **Value types**, including `ImmutableArray<T>`. Note that a default `ImmutableArray<T>` throws on
  most uses too; it is not reported only because nullable annotations cannot describe it.
- `byte[]` and the other "bytes" types. They are a single scalar to protobuf-net rather than a
  collection, and a non-null one — even an empty one — is always written.
- **Surrogated types**, since protobuf-net constructs the surrogate instead.
- `SkipConstructor` on an **abstract type**, which has no effect: it applies to the type actually
  constructed, and a concrete sub-type runs the base constructor as usual. The members are still
  checked as though constructed normally.
- Types whose parameterless constructor chains to another with `: this(...)` — a positional record's
  must — since the chained constructor may assign anything. And types with no parameterless
  constructor at all, which cannot be deserialized; that is `PBN0015`.

## A note on packed scalars

By default protobuf-net writes a zero-length header for an empty `[ProtoMember(IsPacked = true)]`
collection of scalars, so such a member does survive a round-trip between two protobuf-net
endpoints. That is kept only for compatibility with protobuf-net v2: it is switched off by
`RuntimeTypeModel.SkipZeroLengthPackedArrays`, and other protobuf implementations do not write it,
so do not rely on it. The member is reported like any other.
