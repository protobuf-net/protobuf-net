# PBN0028

*'X' is a non-nullable collection, but nothing assigns it when protobuf-net constructs the
instance; it is null whenever the payload does not carry it, and an empty collection is normally
not written at all.*

protobuf has no way to say "present, but empty": an empty collection is simply **not written**. So
on the receiving end the member is never touched, and keeps whatever construction left there. If
that is `null`, a sender holding `[]` leaves the receiver holding `null`.

Nothing warns about this. The member is declared non-nullable, so the compiler is satisfied that
reading it is safe, and the `NullReferenceException` turns up later, somewhere far from the contract,
and only for the messages that happened to have no elements. It is also where protobuf parts
company with JSON, which writes `[]` and so gets the collection back — a DTO that has always worked
with `System.Text.Json` can start failing the day it is sent over protobuf.

The message lists only the fixes that work for that member, and the lightbulb offers them (see
[Fixes](#fixes)). A member that is not a collection is [PBN0030](PBN0030)'s, and the reverse case,
where a nullable member's null comes back as a value, is [PBN0029](PBN0029)'s.

## Without `SkipConstructor`

protobuf-net creates the instance with its **parameterless constructor**, so the collection is safe
if an initializer or that constructor assigns it. It is not safe when nothing does — including the
usual ways of silencing the compiler's own CS8618 warning, which assign nothing at all:

``` csharp
#nullable enable
[ProtoContract]
public class Order
{
    [ProtoMember(1)] public List<OrderLine> Lines { get; set; } = null!;   // reported
    [ProtoMember(2)] public required List<string> Tags { get; set; }        // reported
    [ProtoMember(3)] public List<int> Codes { get; set; } = new();          // fine
}
```

An assignment in a constructor *with parameters* does not count either, since that is not the one
protobuf-net calls — except on an abstract type, where the sub-type may chain to any of them. An
assignment made through a helper marked `[MemberNotNull]` does count, as it does for the compiler.

## With `SkipConstructor`, and on structs

`[ProtoContract(SkipConstructor = true)]` creates the instance without running **any** constructor,
so every field starts out `null` — and that includes initializers, which the C# compiler places
inside the constructor. Here even `= new()` does not help:

``` csharp
#nullable enable
[ProtoContract(SkipConstructor = true)]
public class Order
{
    // the initializer never runs on deserialize: an order with no lines comes back with null here
    [ProtoMember(1)] public List<OrderLine> Lines { get; set; } = new();
}
```

A positional record is the easiest place to hit this, because its primary constructor is the only
thing that assigns the member, and that constructor never runs:

``` csharp
#nullable enable
[ProtoContract(SkipConstructor = true)]
public record TestRecord([property: ProtoMember(1)] string[] Array);

// new TestRecord([]) is written as zero bytes, and comes back with Array == null
```

It is the setting on the **concrete type being read** that counts. On an abstract type it does
nothing, and on a sub-type it strips the members that type inherits just as much as its own — so a
base class is reported when any sub-type it names in `[ProtoInclude]`, at any depth, sets it:

``` csharp
#nullable enable
[ProtoContract, ProtoInclude(10, typeof(Rush))]
public class Order
{
    // an Order is constructed and gets its list; a Rush is not, and comes back with null here
    [ProtoMember(1)] public List<OrderLine> Lines { get; set; } = new();
}

[ProtoContract(SkipConstructor = true)]
public class Rush : Order { }
```

A **struct** contract behaves the same way with or without `SkipConstructor`: protobuf-net reads into
`default(T)` and never calls a constructor, so neither initializers nor an explicit parameterless
constructor run.

## Fixes

**Declare the member nullable.** Offered except on a field that shares its declaration with others
(`List<int> a, b;`), where it would change them all. The value really can be null, and saying so makes
the compiler ask every reader to deal with it; a `= null!` that only silenced CS8618 is removed with
it:

``` csharp
[ProtoMember(1)] public List<OrderLine>? Lines { get; set; }
```

**Initialize it** — `= new()` (or `new List<OrderLine>()` before C# 9), `Array.Empty<T>()` for an
array, or an assignment in the parameterless constructor. Offered only when a constructor actually
runs, so not under `SkipConstructor` or on a struct, and only for an array or a class with a public
parameterless constructor; for an interface type, choose the concrete type yourself.

**Mark it `[NullWrappedCollection]`.** Offered only for a member with `[ProtoMember]`. protobuf-net
then writes the collection inside a wrapper message, which *is* written when the collection is empty,
so an empty collection comes back empty rather than null — with or without `SkipConstructor`:

``` csharp
[ProtoContract(SkipConstructor = true)]
public record TestRecord([property: ProtoMember(1), NullWrappedCollection] string[] Array);
```

> **This changes the wire format.** The field becomes a message whose items sit at field 1, rather
> than a plain `repeated` field. Payloads written before the change, and any peer still on the old
> schema, will not read it correctly; a peer in another language needs the wrapper declared in its
> `.proto` too. Use it where you control both ends, or before the contract has shipped. See
> [null collections](../nullwrappers#null-collections) for the encoding.

**Restore it in a deserialization callback.** protobuf-net runs these on the new instance even when
no constructor ran, so this is the fix for `SkipConstructor` and structs that leaves the wire format
alone. Any of `[ProtoBeforeDeserialization]`, `[ProtoAfterDeserialization]`, `[OnDeserializing]` and
`[OnDeserialized]` satisfies this warning, provided it assigns the member:

``` csharp
[ProtoContract(SkipConstructor = true)]
public class Order
{
    [ProtoMember(1)] public List<OrderLine> Lines { get; set; } = new();

    [ProtoAfterDeserialization]
    public void OnDeserialized() => Lines ??= new();
}
```

A callback is an ordinary method, so it cannot assign a `readonly` field, a getter-only property, or
an `init`-only one — which is what a positional record's parameter becomes — and the message does not
offer it for those.

Make the callback `public`: the runtime model also accepts a non-public one, but the compile-time
(AOT) model does not. In an inheritance hierarchy **only the root's callbacks run** — one declared on
a sub-type is silently ignored, so it does not satisfy this warning. Declare a `virtual` callback on
the root and override it in the sub-type instead.

Or **drop `SkipConstructor`**, if nothing forces it. It is usually there because the type has no
parameterless constructor.

## What is not reported

- **Nullable members** (`List<T>?`), and members in code without nullable reference types enabled —
  those have promised nothing.
- **Value types**, including `ImmutableArray<T>`. Note that a default `ImmutableArray<T>` throws on
  most uses too; it is not reported only because nullable annotations cannot describe it.
- `byte[]` and the other "bytes" types, and types marked `[ProtoContract(IgnoreListHandling = true)]`.
  Both are written even when empty — the first as a single scalar, the second as a message.
- Members already marked `[NullWrappedCollection]`.
- **Surrogated types**, and types with a hand-written `Serializer`, since protobuf-net does not
  construct those itself.
- `SkipConstructor` on an **abstract type**, unless a sub-type sets it too: it applies to the type
  actually read, and a sub-type without it runs the base constructor as usual. The members are still
  checked as though constructed normally. A sub-type added at run time with `AddSubType` is invisible
  to an analyzer, so one that skips construction is not seen.
- Members of a type protobuf-net treats as a **collection** (one implementing `IEnumerable<T>`, without
  `IgnoreListHandling`): it serializes the type as that collection and never reads its members.
- Without `SkipConstructor`: members that are never written — no `[ProtoMember]`, `[DataMember]` or
  `ImplicitFields`. They are whatever the constructor left after `new()` too, which is the compiler's
  business rather than protobuf-net's.
- Without `SkipConstructor`: types whose parameterless constructor chains to another with
  `: this(...)` — a positional record's must — since the chained constructor may assign anything;
  and types with no parameterless constructor at all, which cannot be deserialized (that is
  `PBN0015`).

## Turning it off

This is a warning, and it ships inside protobuf-net.Core, so a project with `TreatWarningsAsErrors`
will see it as an error. To turn it off — for a whole project, or a folder of DTOs — use
`.editorconfig`:

``` ini
[*.cs]
dotnet_diagnostic.PBN0028.severity = none
```

## A note on packed scalars

By default protobuf-net writes a zero-length header for an empty `[ProtoMember(IsPacked = true)]`
collection of scalars, so such a member does survive a round-trip between two protobuf-net
endpoints. That is kept only for compatibility with protobuf-net v2: it is switched off by
`RuntimeTypeModel.SkipZeroLengthPackedArrays`, and other protobuf implementations do not write it,
so do not rely on it. The member is reported like any other.
