# PBN0029

*'X' is nullable, but its initializer gives it a value; null is not written, so a null comes back
as that value.*

protobuf cannot write null for a single value: a null member is simply **not written**. On the
receiving end the member is never touched, so it keeps whatever construction left there. For a
nullable member that is normally `null`, and all is well — unless an initializer gave it something
else:

``` csharp
[ProtoContract]
public class Settings
{
    [ProtoMember(1)] public int? Timeout { get; set; } = 30; // reported
}
```

| sent | received |
| --- | --- |
| `null` | **`30`** |
| `0` | `0` |
| `30` | `30` |

A sender that means "no timeout" leaves the receiver with a 30-second one, and nothing says so. A
zero is fine: an `int?` is written whenever it has a value, zero included.

It is reported wherever an initializer runs on deserialize. `SkipConstructor` belongs to the concrete
type being read, so a base is reported when any type that inherits the member - the base itself, or a
sub-type its `[ProtoInclude]`s reach - is constructed as usual. An abstract base with
`SkipConstructor` is reported unless every concrete sub-type its `[ProtoInclude]`s reach sets it too.

This is [PBN0028](PBN0028) the other way round. There an empty collection is not written, and the
receiver is left with `null` where it expected a value; here a null is not written, and the receiver
is left with a value where it expected `null`.

## With `[NullWrappedValue]`

Wrapping does not help, since a null is still not written, and for numbers and `bool` it makes things
worse. The value inside the wrapper is an ordinary field, which leaves out its default, so a zero or
`false` goes out as an **empty wrapper**. Reading an empty wrapper into a member that already has a
value leaves it alone:

``` csharp
[ProtoMember(1), NullWrappedValue]
public bool? Enabled { get; set; } = true; // null and false both come back as true
```

An enum's zero and an empty string are written inside the wrapper, so for those only null is lost.

## Fixes

**Remove the initializer.** The lightbulb offers this. The default then is `null`, which is what an
absent field reads as, so a null comes back as null and every other value as itself.

If the member also has a `[DefaultValue]`, that has to go too, and the lightbulb removes both. A
declared default is not written, and was only restored by the initializer — without it, the declared
value would come back as `null` instead:

``` csharp
[ProtoMember(1), DefaultValue(30)] public int? Timeout { get; set; } = 30; // reported
[ProtoMember(1)] public int? Timeout { get; set; }                         // fixed
```

**Reset it in a before-deserialization callback**, if the initializer matters for instances built in
code. The callback runs on the new instance before the fields are read, so an absent field reads as
null while `new Settings()` still gets 30:

``` csharp
[ProtoBeforeDeserialization]
public void ResetForDeserialize() => Timeout = null;
```

Make it `public`, since the compile-time (AOT) model does not accept a non-public callback. In an
inheritance hierarchy only the root's callbacks run, as described under [PBN0028](PBN0028). A callback
cannot assign a getter-only or `init`-only property, so the message does not offer it for those, and
with a `[DefaultValue]` it works only once that is removed, for the reason above.

Either way there is a trade: a payload written before the member existed now also reads as `null`
rather than as 30. protobuf cannot tell "sent as null" from "not sent", so no contract can have both.

`IsRequired` does not help, since it does not change what an absent field reads as, and
`[DefaultValue]` makes things worse, as above. So on a nullable member the analyzer does not suggest
either: PBN0020 and PBN0022 stay quiet there.

## What is not reported

- `SkipConstructor` on every concrete type that carries the member, and struct contracts: no initializer runs
  on deserialize, so the null survives.
- Members without `[ProtoMember]`. One serialized some other way — `ImplicitFields`, or
  `[DataMember(Order = …)]` — loses its null just the same, but only `[ProtoMember]` is checked.
- Members whose presence is tracked with a `{Name}Specified` property, which is assigned on read, so
  the receiver can tell. A `ShouldSerialize{Name}()` method is no help — it only decides what is
  written — so those *are* reported.
- Members that a *before*-deserialization callback assigns (`[ProtoBeforeDeserialization]` or
  `[OnDeserializing]`). An after-deserialization callback runs once the fields are read, too late to
  tell a null that was sent from one that was not, so it does not count.
- A collection without `[NullWrappedCollection]`. protobuf-net writes nothing for null and nothing for
  empty, so one of them comes back as the other with or without an initializer; that is the wire
  format, not the initializer. With `[NullWrappedCollection]` the two are told apart, and then the
  initializer is what loses the null, so it is reported.
- An initializer that is null: `= null`, `= default`, `(int?)null`. Note that `default(int)` on an
  `int?` is a zero, not a null, and is reported.
- An assignment in the constructor, or an initializer on a field behind the property
  (`int? _timeout = 30;` read by `Timeout => _timeout`). Only the `[ProtoMember]`'s own initializer is
  checked.
- Surrogated types, types with a hand-written `Serializer`, and types protobuf-net treats as a
  collection, whose members it never reads.
- Nullable reference types in code without nullable annotations enabled, which have promised nothing.
  `int?` and other `Nullable<T>` types are nullable regardless, and are reported.

## Turning it off

``` ini
[*.cs]
dotnet_diagnostic.PBN0029.severity = none
```
